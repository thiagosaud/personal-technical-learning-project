## 📦 Versioning

Versioning uses [Changesets](https://github.com/changesets/changesets) and
follows Semantic Versioning.

Changesets separates the description of a change from the release operation.
The change is recorded locally first, then the GitHub Actions release workflow
turns pending changesets into a versioning pull request and, after that pull
request is merged, into a release and Git tag.

### Versioning lifecycle

#### 1. Create a changeset locally

After implementing a change, run:

```bash
pnpm run changeset
```

The interactive CLI asks which workspace package was changed and whether the
release is a `patch`, `minor`, or `major` change. It then creates a Markdown
file inside `.changeset/`. That file is the release note source, not the final
changelog.

The selected increment should reflect the public impact of the change:

| Increment | Use when                                                           |
| --------- | ------------------------------------------------------------------ |
| `patch`   | Fixes or internal improvements that preserve the existing contract |
| `minor`   | Adds backward-compatible functionality                             |
| `major`   | Introduces a breaking change to the package contract               |

Review the generated file, commit it with the implementation, and push the
branch. The repository CI validates the pull request independently from the
release workflow.

#### 2. Preview changesets since `main`

To inspect changesets created after the current `main` branch:

```bash
pnpm run changeset:auto
```

This runs Changesets with `--since main`. It is useful for reviewing the
pending release scope before merging, but it does not publish a release by
itself.

#### 3. Enter or leave prerelease mode

For a prerelease cycle, use:

```bash
pnpm run changeset:pre-enter
pnpm run changeset:pre-exit
```

The first command enters the `rc` prerelease mode. The second exits that mode
after the release candidate cycle is complete. These commands update the
Changesets state files and must be reviewed and committed like any other
release metadata.

#### 4. What happens on GitHub

The workflow in
[.github/workflows/release.yml](.github/workflows/release.yml) runs on pushes
to `main` or `master` and performs the following steps:

1. Checks out the complete Git history.
2. Installs Node.js `22` and the pinned pnpm `11.22.0` toolchain.
3. Installs dependencies with `pnpm install --frozen-lockfile`.
4. Runs `changesets/action@v1` with the local version command
   `pnpm run changeset:version:packages`.
5. If pending changesets exist, opens or updates the `Version Packages` pull
   request with package version changes and changelog entries.

The action uses the repository `GITHUB_TOKEN` with permission to write package
contents and pull requests. It does not release directly from the feature
branch. The generated versioning pull request is the review and approval
boundary for the release.

#### 5. Version the packages locally

The command executed by the workflow is also available locally:

```bash
pnpm run changeset:version:packages
```

It runs two operations:

1. `changeset version` consumes pending changesets, updates the affected
   `package.json` files, and writes changelog entries.
2. `pnpm install --no-frozen-lockfile` refreshes the pnpm lockfile after those
   manifest versions change.

This command is intended for the automated release action and for local
inspection. It changes working-tree files; review the diff before committing.

#### 6. Merge and publish the release

After the `Version Packages` pull request is reviewed and merged, the merge
pushes to `main` and triggers the workflow again. With no pending changesets,
the Changesets action completes the release step and creates the configured
Git tags/releases. The root package and subproject package are versioned
independently according to the package selected in each changeset.

The repository configuration keeps private workspace packages versionable via
`privatePackages.version: true`, while package publication access remains
restricted.

### Available package scripts

The scripts below are defined in [package.json](package.json). Run them from
the repository root with `pnpm run <script>`.

#### Installation and lifecycle

| Script                       | What it does                                                                                                                      |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `prepare`                    | Installs Lefthook Git hooks after dependencies are installed. pnpm runs this lifecycle script automatically.                      |
| `changeset`                  | Opens the interactive Changesets CLI to create release metadata for a changed package.                                            |
| `changeset:auto`             | Lists or processes changesets relative to `main` using `changeset --since main`; it does not publish a release.                   |
| `changeset:pre-enter`        | Enters the `rc` prerelease mode.                                                                                                  |
| `changeset:pre-exit`         | Leaves prerelease mode after the candidate cycle.                                                                                 |
| `changeset:version:packages` | Applies pending changesets, updates versions and changelogs, then refreshes `pnpm-lock.yaml` without frozen-lockfile enforcement. |

#### Commit and branch validation

| Script        | What it does                                                                                    |
| ------------- | ----------------------------------------------------------------------------------------------- |
| `lint:commit` | Validates the current commit message with Commitlint and the conventional commit configuration. |
| `lint:branch` | Validates the current Git branch name against the repository branch naming rules.               |

#### Markdown and JavaScript tooling

| Script              | What it does                                                                                                     |
| ------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `lint:markdown`     | Checks Markdown files with Markdownlint.                                                                         |
| `lint:markdown:fix` | Applies Markdownlint automatic fixes.                                                                            |
| `lint:code:js`      | Checks repository-supported JavaScript, JSON, Markdown, and configuration formatting with Prettier.              |
| `lint:code:js:fix`  | Applies Prettier formatting to the repository.                                                                   |
| `format:js`         | Formats the repository with Prettier; this is the write variant of the JavaScript/configuration formatting step. |

#### Python quality and formatting

| Script             | What it does                                                                         |
| ------------------ | ------------------------------------------------------------------------------------ |
| `lint:code:py`     | Runs Ruff lint checks using the root Python configuration.                           |
| `lint:code:py:fix` | Runs Ruff lint checks and applies safe automatic fixes.                              |
| `format:py`        | Formats Python files with Ruff format.                                               |
| `test:py`          | Runs the configured Pytest suite with the frozen root environment.                   |
| `lint:all:fix`     | Runs Markdownlint fixes, Prettier, Ruff lint fixes, and Ruff formatting in sequence. |

#### Security and CI

| Script                  | What it does                                                                                          |
| ----------------------- | ----------------------------------------------------------------------------------------------------- |
| `lint:security:py`      | Runs Bandit with `.bandit.yaml` for Python security analysis.                                         |
| `lint:security:semgrep` | Runs Semgrep with the repository rules and the `p/security-audit` ruleset; findings fail the command. |
| `security:secrets`      | Runs Gitleaks with verbose output and redacted findings.                                              |
| `security:sonar`        | Starts the configured SonarQube scanner. It requires a working SonarQube environment.                 |
| `test:ci:local:all`     | Runs the pull-request workflow locally through `act` using the Linux AMD64 container architecture.    |
